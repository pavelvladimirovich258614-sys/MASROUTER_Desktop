# Теория MASROUTER (arXiv:2502.11133)

## Зачем это всё

Современные LLM-приложения часто строятся как **multi-agent systems (MAS)**: несколько агентов, у каждого своя роль, они общаются по цепочке или в графе. MAS дают лучшее качество, но **дороже**: каждый вызов LLM стоит денег, и архитектура с 5 агентами может стоить в 5 раз больше, чем один агент.

**Вопрос**: как автоматически выбрать архитектуру MAS под конкретную задачу, чтобы балансировать качество и стоимость?

**Ответ статьи MasRouter** — обучить policy gradient, который решает 3 подзадачи:
1. **Какую топологию** выбрать (Chain, Tree, FullConnected, Debate, Reflection, …).
2. **Какие роли** назначить агентам (MathAnalyst, Inspector, …).
3. **Какие LLM** использовать для каждого агента (GPT-4o, Claude, Gemini, …).

## Формализация

**MASR (Multi-Agent System Routing)**: при наличии пула LLM, режимов collaboration и возможных ролей агентов, оптимальный MAS Router для любого запроса `q` должен:
1. Определить подходящие режимы multi-agent collaboration.
2. Эффективно распределить роли агентов.
3. Назначить соответствующий LLM каждому агенту.

Тем самым — балансировать производительность и стоимость.

## Каскад Fθ = Fθm ∘ Fθr ∘ Fθt

```
Fθt : Q → T              (collaboration determiner)
Fθr : (Q, T) → {R_i}     (role allocator)
Fθm : (Q, T, {R_i}) → {M_i}  (LLM router)
```

Каскад применяется последовательно: сначала выбирается топология, затем под неё — цепочка ролей, затем под каждую роль — модель.

## Целевая функция

```
max_θ  E[ U(S; Q, a) − λ · C(S; Q) ]
```

- `U` — полезность (качество).
- `C` — стоимость.
- `λ` — параметр trade-off ∈ {5, 15, 25}.

Чем меньше λ, тем больше мы ценим качество (дорого). Чем больше — тем больше экономим (рискуя качеством).

## Численные константы (раздел 5.1)

| Параметр | Значение | Смысл |
|---|---|---|
| `α` | 0.01 | Learning rate |
| `τ` | 1 | Температура |
| `γ` | 6 | Максимум агентов |
| `λ` | {5, 15, 25} | Trade-off |
| `K` | {5, 10} | Итерации policy gradient |

## Число агентов

```
k = ⌈δ(H) · γ⌉
```

`δ(H) ∈ [0, 1]` — обучаемая функция сложности. `γ = 6` — максимум.

## Гамма-функция (формула 12)

```
C(k; n_1, …, n_Nm) ≈ Γ(δ(H)·γ + 1) / [Γ(n_1+1)·…·Γ(n_Nm+1)]
```

Γ(z) — расширение факториала на вещественные числа. В MASROUTER Desktop реализована через Lanczos approximation.

В UI это отображается как **Topological Multiplier = Γ(k+1)**.

## Ablation Study (Таблица 3)

| Вариант | GSM8K | $ | MATH | $ |
|---|---|---|---|---|
| Vanilla MasRouter | 95.45 | 1.59 | 75.42 | 3.58 |
| w/o Fθt | 93.84 | 2.38 | 72.77 | 4.48 |
| w/o Fθr | 94.70 | 1.67 | 73.01 | 3.63 |
| **w/o Fθm** | **93.36** | **1.98** | **71.08** | **4.16** |
| w/o C(·) | 95.63 | 2.45 | 75.18 | 5.07 |

**Главный вывод**: без Fθm — самое большое падение performance (−2.09% GSM8K, −4.34% MATH). Это доказывает, что **выбор модели критичен**.

## Sensitivity (раздел 5.5)

**γ** (число агентов): 2→6 даёт +2.12% performance; γ>6 даёт ×1.5 cost без значимого прироста.
**λ** (trade-off): 5→25 снижает overhead на 17.78% при падении performance всего на ~1.3%.

## Как MASROUTER Desktop реализует каскад

В нашей реализации каскад **детерминированный, rule-based**:

1. **Fθt** (collaboration determiner) — набор правил по типу задачи, риску, сложности.
2. **Fθr** (role allocator) — набор правил по режиму ECO/BALANCED/QUALITY и флагам риска.
3. **Fθm** (LLM router) — выбор модели по тиру (cheap/balanced/strong).

LLM внутри роутера **не используется** — это компромисс ради простоты и предсказуемости. В production-версии можно добавить LLM-советник для edge cases.

См. `src/main/routerEngine.ts` для реализации.
